Prism, formerly FinReq · Project guide

Turn a stakeholder interview into policy-mapped requirements, reviewed by a person.

Prism is an agentic, multi-agent LLM system for requirements engineering and SDLC model recommendation in financial services. It extracts requirements from a transcript, checks them against sample policies, scores risk, ranks delivery models and writes the paperwork. Nothing is final until a person accepts it.

01

What Prism is

Prism reads a stakeholder interview and produces the artefacts a delivery team needs: a software requirements specification (SRS), user stories, a traceability matrix, a compliance-control matrix, a risk register and an SDLC plan. Every step that a regulator or auditor would ask about leaves a record.

Domain

Financial services. The first use case is loan origination, following the problem statement's advice to begin with one. Sample policies in the knowledge base are fictional and labelled as such.

Agentic and multi-agent

One coordinator, run_pipeline(), calls each agent in a fixed order and shares one context. Four agents call a language model. Five are deterministic Python, because quality, conflict, risk, security and validation judgments must be explainable and reproducible for an audit.

Human in the loop

Requirements change state only through an explicit human action: accept, reject, edit or regenerate. The SDLC choice needs four role sign-offs. The compliance agent never makes a legal determination.

Naming

Prism is the product and the web UI brand. The repository, the Python package (finreq), the CLI and the FINREQ_* environment variables keep the original name, FinReq.

The problem it solves

Requirements for a financial product start as a conversation. A loan officer explains how an application should be assessed, a compliance officer names the rules, a security officer lists the controls. An analyst then has to turn that talk into requirements that are testable, traceable to who said them, mapped to policy, and risk-rated, and then pick a delivery method. That work is slow, and traceability is usually lost on the way. Prism does the drafting and the cross-checking. People make every decision.

What goes in and what comes out

In

  • A stakeholder interview transcript (pasted, uploaded as .txt, or the bundled sample).
  • The stakeholder role and a domain tag, such as loan_officer and LOAN.
  • An optional SDLC project profile: nine factors a person sets with sliders.
  • A folder of policy documents (the knowledge base).

Out

  • Requirements with category, priority, acceptance criteria, a verbatim source quote, quality issues, policy evidence, risk level and a status.
  • A ranked list of ten delivery models, with reasons for and against each.
  • One zip of nine files: SRS, user stories, requirements CSV, traceability matrix, compliance matrix, risk register, open issues, assumptions and dependencies, SDLC plan.
  • An audit trail of every model call, retrieval and human decision.

The six ideas the design rests on

1. One coordinator, many small agents

Each agent does one narrow job and mutates the requirement it is given. run_pipeline() calls them in a fixed order. There is no agent-to-agent chatter, so a run is easy to trace and to replay.

2. Use a model only where language is the job

Four agents read or write natural language, so they call an LLM. Everything that scores, routes or checks is plain Python with fixed thresholds. The same input always gives the same routing, which an auditor can reproduce.

3. Ground every compliance claim in a document

The compliance agent may only restate what a retrieved policy passage says. It must cite the passage. If nothing relevant is found it records a gap instead of guessing. See Retrieval (RAG).

4. Never show the model real personal data

Emails, card numbers, PAN, IFSC, phone and account numbers are replaced by placeholders before any agent runs, and restored only for the human-facing screens. See Masking and model backends.

5. A person has the last word

Automated stages can only route a requirement to needs clarification or pending review. Only an explicit accept, reject, edit or regenerate changes the status afterwards. The delivery model needs four sign-offs.

6. Everything leaves a record

Every model call and retrieval is an audit event. Every decision is an approval record. Both are stored in SQLite and can be viewed per project in the UI.

A requirement, start to finish

The sample interview has the loan officer say, roughly, that applicants must be verified before a loan decision. Here is what happens to that sentence.

  1. Mask. Any PAN or phone number in the text becomes [PAN_1] or [PHONE_1].
  2. Extract. The model returns a statement such as “The system shall verify the applicant’s identity before a loan decision is made”, with a priority, acceptance criteria, a justification and the verbatim quote it came from.
  3. Classify. It gets categories such as functional and regulatory.
  4. Quality check. Rules look for vague words, a missing “shall”, missing acceptance criteria or source, unknown acronyms and impossible promises.
  5. Compare. The conflict agent checks it against the other requirements for duplicates and contradictions.
  6. Compliance. The KYC policy passage scores highest in retrieval. The model states the control it requires, citing that passage.
  7. Security, risk, validation. It is tagged, scored (for example high) and routed to pending review if no blocking issue remains.
  8. Unmask and save. Real values return to the display fields and the requirement is stored.
  9. Review. A person opens it, reads the evidence trace, and accepts, rejects, edits or regenerates it.

FinReq was itself built with the model it recommended for itself, an Agile-DevSecOps hybrid. See docs/SDLC.md.

How to run it

Needs Python 3.11 or later and Node.js 24 or later, and one model backend.

Install and build the app

pip install -r backend/requirements.txt
npm ci --prefix frontend
npm run build --prefix frontend
python backend/server.py

Open http://127.0.0.1:8000. The server serves the API and the built React front end from one process. For front-end work, run npm run dev --prefix frontend (port 5173, which proxies /api to backend/server.py on port 8000).

Choose a model backend

BackendDefault modelKeyNotes
Ollama qwen2.5:3b-instruct None, runs locally Run ollama pull qwen2.5:3b-instruct, then keep ollama serve running. About three times faster than the 7B fallback, but it recalls fewer requirements. Use hhao/qwen2.5-coder-tools:7b when recall matters more than time.
Gemini gemini-3.5-flash-lite GEMINI_API_KEY About 32 calls per analysis. The free tier allows 15 a minute and 500 a day, so expect a run to take minutes. Override with FINREQ_GEMINI_MODEL.
Groq openai/gpt-oss-120b GROQ_API_KEY Free plan. The model dropdown lists Groq's chat models from GET /api/groq/models. Override with FINREQ_GROQ_MODEL.

API keys come only from the environment. Set GEMINI_API_KEY or GROQ_API_KEY in the shell that starts the server, or put it in a .env file at the repo root. .env is gitignored. A value in the shell wins over .env. No key is accepted as a constructor argument, CLI flag, API route or UI field, and keys are never placed in URLs.

Use it in the browser

  1. Transcript. Name the project, paste or upload a transcript, or choose the sample interview. Then analyse (Ctrl or Cmd+Enter). The run view shows each stage as it happens.

  2. Review. Triage requirements in the list or on the risk map. The inspector shows the evidence trace. Keys: j and k move, a accepts, r rejects, e edits. Answer follow-up questions to re-run with the answers added.

  3. Delivery model. Ten models are ranked by fit. Choose one, adjust the project profile if needed, then collect the four sign-offs.

  4. Export. Download the nine artefacts as one zip. The audit trail lists every decision and model call for the analysis.

Every analysis is kept under Projects and survives a server restart.

Run it from the command line

python backend/cli.py --transcript backend/data/fixtures/loan_officer_interview.txt --role loan_officer \
    --domain LOAN --profile backend/data/fixtures/loan_project_profile.json --out out

# add --backend gemini (or groq) and --model to choose a backend

Check it

python -m pytest                          # no Ollama needed (FakeLLMClient)
python backend/scripts/gates.py                   # every gate: tests, eval floors, bandit, secret scan, web build, audits
python backend/eval/evaluate.py                   # offline benchmarks
python backend/eval/evaluate.py --live            # live extraction eval (needs ollama serve)

Why some agents are rule-based. Quality, conflict, risk, security, validation and the SDLC engine are pure Python so that their judgments can be explained and reproduced for an audit. Interaction, extraction, classification and compliance need a model to read natural language.

How each agent decides

Interaction

LLM

Looks at the masked transcript across fixed topic areas (such as data collection and retention) and asks a question where a topic is missing or vague. Optional. Answers are appended to the transcript and the run is repeated.

Extraction

LLM

Prompted to return JSON: statement, priority, acceptance criteria, business justification and a verbatim source excerpt. IDs look like FR-LOAN-001 and continue from the highest stored number for that prefix.

Classification

LLM

Picks one or more of 13 categories: business, stakeholder, functional, security, privacy, regulatory, performance, availability and reliability, usability, data management, integration, audit and reporting, operational and maintenance.

Quality check

rule

Flags: vague words (“fast”, “appropriate”, “seamless”), no shall/must/will/should, no acceptance criteria, no justification, no source quote, an unknown ALL-CAPS acronym, and absolute promises (“100% accuracy”, “zero downtime”). No criteria plus vague language also means not testable.

Conflict detection

rule

Compares every pair with TF-IDF cosine similarity. At 0.75 or more, a pair that differs by a negation or by numbers (“2 seconds” vs “5 seconds”) is a conflict. At 0.92 or more without that difference it is a duplicate.

Compliance

LLM

Retrieves policy passages, then asks the model which are relevant and what control each requires. Low similarity or “not relevant” becomes a recorded gap. Details in Retrieval (RAG).

Security and privacy

rule

Keyword lists (encrypt, MFA, session, token, consent, retention, erasure and more) add the security or privacy category. If it touches those areas and has no compliance mapping without a gap, it adds a missing-control issue for a security or compliance officer.

Risk analysis

rule

Score = highest category base (0.30 for security, privacy or regulatory; 0.20 for audit) + priority weight (critical 0.30, high 0.20, medium 0.10) + 0.15 per compliance gap (max 0.30) + 0.05 per other issue (max 0.20) + 0.20 if in conflict. Levels: low under 0.25, medium from 0.25, high from 0.50, critical from 0.70.

Validation

rule

Any ambiguity, incompleteness, not-testable, missing-source, undefined-term, infeasibility or inconsistency issue routes to needs clarification. Otherwise pending review. Compliance gaps and duplicates do not block: they raise the risk score and go to a human.

Retrieval is TF-IDF with cosine similarity over backend/data/knowledge_base/*.md, in retrieval.py (KnowledgeBase L88). It is dependency-free and fully offline. There is no vector database.

05

Retrieval (RAG)

RAG means retrieval-augmented generation: look up trusted text first, then let the model answer using only that text. Prism uses it for one job, mapping a requirement to policy. The model never answers from memory about what a policy says.

The loop, for one requirement

  1. Retrieve. KnowledgeBase.retrieve(statement) scores every policy document against the requirement and returns the top 3, each with its source, jurisdiction, effective date, version, a 400-character excerpt and a similarity score.
  2. Log. The retrieval and its scores are written to the audit log.
  3. Check confidence. If the best score is under 0.18 (or nothing matched), the model is not called. A gap is recorded: “no confident compliance mapping found”.
  4. Generate, grounded. The prompt lists the passages as numbered evidence and says to use only them and never outside knowledge. The model returns JSON: for each relevant passage, its index, the concrete control the requirement must satisfy, and a gap if the passage is unclear.
  5. Attach citations. Each mapping keeps the passage it came from, its jurisdiction and its similarity as confidence. Indexes outside the evidence list are ignored.
  6. Escalate. If the model says nothing is relevant, or reports a gap, a missing-control issue is added. The risk score rises and a person decides.

Strong match

Score at or above 0.18 and the model finds a control. A mapping is stored with its citation. No gap.

Weak match

Score under 0.18. No model call. A gap and a missing-control issue say a compliance officer must resolve it.

Retrieved but irrelevant

Score is fine but the model judges the passage does not apply. Same escalation, worded as “evidence not judged relevant”.

Relevant but incomplete

The model maps the control and also states what is missing. The mapping is kept and the gap is shown beside it.

How retrieval works

  • Index. At start-up every .md or .txt file in backend/data/knowledge_base/ is read. A header gives source, jurisdiction, effective_date, version and applicability. The bodies are vectorised once with TF-IDF.
  • Query. The requirement statement is vectorised with the same vocabulary. Cosine similarity against every document gives the scores. Zero scores are dropped.
  • Domain stop words. “system”, “shall”, “must”, “customer” and similar words appear in every requirement and every policy. They are removed so real topic words decide the ranking. The 0.18 cut-off was tuned on the sample set: unrelated queries score about 0.10, the weakest true match about 0.20.
  • Provenance. The header fields travel with each passage into the UI, the compliance matrix and the audit log, so every claim shows where it came from and which version.
Sample policy (fictional)Covers
kyc_onboarding_policy.mdIdentity verification and onboarding.
data_privacy_consent_policy.mdPersonal data, consent, retention.
audit_reporting_policy.mdAudit logs and reporting.
transaction_security_policy.mdTransaction authentication and security.
credit_decisioning_fairness_policy.mdFair, explainable credit decisions.

Honest limits. TF-IDF matches words, not meaning, so a paraphrase with no shared vocabulary can score low and become a gap. That is the safe failure: gaps go to a human. The sample policies are fictional, and the output is not legal advice. To use real policies, drop files with the same header into the folder. To use embeddings or a vector database, replace only retrieval.py: callers use just retrieve().

06

Masking and model backends

Masking: the model never sees real identifiers

Before any agent runs, mask_text() replaces sensitive values with stable placeholders and keeps a reverse map in memory. The same value always gets the same placeholder inside one run, so the model can still tell “the same account, mentioned twice”. After every agent has finished, the map restores real values into the fields people read.

KindPlaceholderMatches
Email[EMAIL_1]name@host.tld
Card[CARD_1]16 digits, with spaces or dashes
Aadhaar[AADHAAR_1]three groups of four digits
PAN[PAN_1]five letters, four digits, one letter
IFSC[IFSC_1]four letters, 0, six characters
Phone[PHONE_1]ten digits starting 6 to 9, optional country code
Account[ACCOUNT_1]any other run of 9 to 18 digits

Specific patterns run first, so a card number is not swallowed by the generic account pattern. This is a regex classifier for a prototype, not a production PII scanner. Names are not masked. See masking.py.

Model backends

Ollama (default)

Local server, no key, nothing leaves the machine. Default qwen2.5:3b-instruct, about three times faster than the 7B fallback but with lower recall. The model picker lists whatever you have pulled.

Gemini

Google API. Key from GEMINI_API_KEY only, sent in a header, never in a URL. Default gemini-3.5-flash-lite. Retries 429 and 503 with growing waits; a daily-quota failure stops at once.

Groq

OpenAI-compatible API. Key from GROQ_API_KEY only. Default openai/gpt-oss-120b with low reasoning effort. Uses JSON mode. The server fetches the model list so only ids reach the browser.

Fake client (tests)

FakeLLMClient returns scripted answers, so the whole suite and the API tests run with no model and no network.

Making small models dependable

  • JSON repair. generate_json() parses the reply. On failure it re-prompts with the bad output and the parse error, up to two retries, then raises LLMError.
  • Unwrap. Small models often wrap one object in a one-item array. unwrap_single() removes the wrapper in one place for interaction, classification and compliance.
  • Audit. Agent.call_llm_json() logs every call, so the audit trail shows each model call for a project.
  • Keys. Nothing accepts a key through a flag, API route or UI field. Error messages carry the provider text, never the key.

Code: llm.py (build_llm_client, generate_json, unwrap_single) · config.py.

The SDLC engine

sdlc.py recommends a delivery model. It is deliberately not part of run_pipeline(), because it depends on a project profile that a person supplies. It is recomputed whenever a slider moves: rank(derive_factors(reqs, profile)).

derive_factors L75

Four factors come from the requirements. Nine come from the project profile. A profile value can override a derived one. Requirement stability measures how clear the requirements are, not how often scope changes; volatility belongs in the human-set change-frequency factor.

rank L111

Weighted multi-criteria scoring, which is explainable term by term. It sorts on the unrounded score, so two models that round to the same percentage are still ordered. Ten models are ranked, and the top five are shown first.

workflow L204

Phases for each model, with financial controls built in and exit gates for each phase. render_plan (L208) turns the chosen model into the SDLC plan artefact.

Four sign-offs

Project manager, architect, security lead and compliance officer (SDLC_APPROVER_ROLES). A choice is baselined only when all four have signed off on that specific model. Sign-offs are approval records in the audit trail.

Security and audit

Prism is a prototype. It implements the controls below and states plainly what it does not.

Implemented

  • PII masking boundary. The transcript is masked once at ingestion, before any LLM call. Real values are restored only after every agent has run, and only in human-facing fields. Prompts stay masked throughout.
  • Audit events. Every LLM call and every retrieval is an AuditEvent (models.py L152).
  • Approval records. Every human decision on a requirement or an SDLC sign-off is an ApprovalRecord (L141). Only agents/approval.py changes approval status after validation.
  • Environment-only keys. GEMINI_API_KEY and GROQ_API_KEY are read only from the shell or the gitignored .env. Gemini uses the x-goog-api-key header and Groq a Bearer header, so keys never appear in URLs, logs or the UI. Key-shaped strings outside .env fail the secret-scan gate.
  • Gates. backend/scripts/gates.py runs tests, eval floors (quality F1 at least 0.95, conflict accuracy at least 0.85), bandit, a secret scan of git-tracked files, the front-end build with npm audit, and pip-audit. CI runs the same script.
  • Offline retrieval. Policy lookup needs no network.

Not implemented

  • Role-based access control (RBAC). The "reviewing as" role is a label, not an access check.
  • Multi-factor authentication (MFA).
  • Encryption at rest. The SQLite database is plain.
  • Session isolation.

Out of scope for a prototype. Compliance output is a mapping for human review, not legal advice.

Known limitations

These were found in real runs, not hypothetically. The project notes list them in full.

  • Small models sometimes omit business justifications. The 3B model can leave every justification out of a run. Every requirement is then flagged incomplete, and the stability factor drops to 0. The rules are working as intended; rerun or use the 7B model.
  • Small models wrap one object in an array. Fixed in unwrap_single(), used by interaction, classification and compliance.
  • Duplicate detection misses paraphrases. TF-IDF cannot see meaning. Semantic embeddings would be needed (conflict benchmark case C2).
  • The 7B model is conservative about compliance. Clearly related policies are escalated as gaps. Do not lower the threshold to hide them; a gap goes to a human, which is the safe failure mode.
  • Audit events carry no analysis id. The audit tab picks a run's model calls by time window, so two runs started at the same moment would show each other's calls. Decisions are matched exactly.
  • Sample policies are fictional. The knowledge base is labelled as fictional, so compliance output is not legal advice.
  • Free-tier keys hit limits. One analysis can exceed the Gemini free quota. Retries wait for Google's delay, but a wait over 60 seconds fails at once. Groq behaves the same way. Groq has not yet been measured with the live eval.
  • Stale SQLite threads. Store needs check_same_thread=False because the API serves requests and runs analyses on different threads. Check this again if SQLite is ever replaced.

Measured model results are in README. On the loan-officer fixture, the 3B default reaches F1 0.692 in about 81 seconds, and the 7B fallback reaches F1 0.774 in about 211 seconds. Each row is a single run.
